# 동시성 테스트 설계 (매칭)

## 목적
- 현재 비관적 락(FOR UPDATE) 기반 매칭의 안정성과 중복 매칭 방지 여부를 검증
- 낙관적 락 전환 시 재시도 비용/충돌률을 비교하기 위한 기준 확보

## 비관적 락 vs 낙관적 락 (최소 비교)
- **비관적 락(FOR UPDATE)**: 선택한 행을 트랜잭션 종료까지 잠그며, 다른 트랜잭션의 `UPDATE/DELETE/SELECT FOR UPDATE`는 대기 또는 실패(`NOWAIT`) 처리됨.
- **낙관적 락(버전 체크 + 재시도)**: 락 대기 대신 충돌 시 재시도. 충돌률이 높으면 재시도 폭증 가능.
- **의사결정 포인트**: 충돌 빈도(낮음=낙관적, 높음=비관적), 응답시간/처리량 목표, 재시도 허용 범위.

## 테스트 방식 (필수만)
### 시나리오 1: 동시 매칭 요청 경합
- 동일 조건 사용자 N명이 동시에 매칭 요청
- 기대 결과: 중복 매칭 0건, 동일 사용자 중복 매칭 0건

### 시나리오 2: 큐 삽입 vs 매칭 처리 경합
- 대기열 삽입 요청과 매칭 처리(매칭 트랜잭션) 동시 수행
- 기대 결과: 큐 중복 삽입 0건, 매칭 실패/충돌 최소화

## 측정 지표 (최소)
- 평균/95p 매칭 응답시간
- 트랜잭션 실패/재시도 횟수
- 락 대기 발생 여부(`NOWAIT` 기준 실패 건수 또는 대기 시간 로그)

## 수집 정보 (최소)
- 응답 코드 및 에러 유형(재시도 필요 여부)
- 요청 수 대비 매칭 결과 건수
- 중복 매칭/중복 큐 삽입 발생 여부

## 판정 기준
- 중복 매칭 0건
- 중복 큐 삽입 0건
- 실패/재시도 비율이 허용 범위 내

## 참고 (PostgreSQL)
- `SELECT ... FOR UPDATE` 행 락 동작 및 차단/대기
- `NOWAIT`/`SKIP LOCKED` 옵션 동작
- `SKIP LOCKED`는 큐와 같은 다중 소비자 처리에 유용하지만 일관성 뷰가 아님
